# EduProgram - Технические решения

В блоке технических решений будут приведены описания выбора алгоритмов и инструментов для реализации проекта.

## 1. Перевод программ

Для работы с программами международных вузов необходимо было реализовать перевод рабочих программ. Для этого есть несколько готовых библиотек, которые мы изучили и на их основе выбрали наиболее подходящую.

### 1.1 Google Translate

**Преимущества:**
- Огромный охват языков — поддерживает около 250 языков, включая многие редкие и исчезающие.
- Качество для глобальных языковых пар — отлично справляется с переводами между английским, испанским, китайским, арабским и французским — самыми распространёнными языками мира.
- Бесплатная интеграция.

**Недостатки:**
- Зависимость от интернета — хотя есть офлайн-режим, он урезан по функциональности и качеству по сравнению с онлайн-версией.

### 1.2 Yandex Translate

**Преимущества:**
- Хорошее качество для русскоязычных пользователей — показывает хорошие результаты при переводе на русский язык.
- ИИ-режим — на основе большой языковой модели позволяет переводить с учётом глубокого контекста.

**Недостатки:**
- Платная интеграция.
- Зависимость от интернета — хотя есть офлайн-режим, он урезан по функциональности и качеству по сравнению с онлайн-версией.

### 1.3 DeepL Translate

**Преимущества:**
- Высокое качество перевода для европейских языков — DeepL стабильно получает наивысшие оценки от профессиональных лингвистов за естественность и плавность перевода.
- DeepL Write — помимо перевода, сервис предлагает инструмент для улучшения грамматики.
- Бесплатная интеграция.
- Не зависит от интернета.

**Недостатки:**
- Из-за независимости от интернета пакет имеет большой объём → нет возможности поместить его в Docker-контейнер.
- Хуже переводит по сравнению с уже рассмотренными библиотеками.

### Вывод

**Google Translate** выбран как оптимальное решение, сочетающее высокое качество перевода для требуемых языков, бесплатность, простоту интеграции и возможность работы в Docker-контейнере.  

**Yandex Translate** оказался платным, а **DeepL Translate** — слишком тяжёлым для контейнеризации и при этом показывает худшее качество перевода.

## 2. Библиотека для отрисовки графов

В рамках реализации проекта необходимо было визуализировать учебные программы и их взаимосвязи. Для этого были рассмотрены несколько популярных библиотек для отрисовки графов.

### 2.1 D3.js

**Преимущества:**
- Максимальная гибкость — поддержка любых кастомных визуализаций.

**Недостатки:**
- Требует много кода даже для простых задач.
- Скорость падает при больших объёмах данных.
- Нет встроенных layout-решений «из коробки».

**Вывод:** мощный инструмент, но не оптимален для задач, где важна скорость разработки и производительность.

### 2.2 Vis.js (vis-network)

**Преимущества:**
- Простота использования.
- Быстрая настройка.

**Недостатки:**
- Ограниченная кастомизация.
- Производительность ухудшается при большом количестве узлов (>1000).
- Layout деревьев не всегда читаемый.

**Вывод:** подходит для небольших графов, но не масштабируется.

### 2.3 React Flow

**Преимущества:**
- Удобен в React-приложениях.
- Хороший пользовательский опыт (UX).

**Недостатки:**
- Не самый легковесный.
- Требует дополнительных решений для layout.
- Производительность средняя.

**Вывод:** больше подходит для UI-редакторов, чем для работы с большими графами.

### 2.4 Cytoscape.js + dagre

**Преимущества:**
- Высокая производительность даже на больших графах.
- Поддержка layout через dagre (оптимально для деревьев).
- Хорошая читаемость структуры.
- Относительно легковесный.
- Простая интеграция.

**Недостатки:**
- Меньше UI-решений, чем у React Flow.

### Сравнение библиотек

| Библиотека | Скорость | Лёгковесность | Читаемость графа | Итог |
|------------|----------|---------------|------------------|------|
| D3.js | Средняя | Высокая | Зависит от реализации | Сложно |
| Vis.js | Низкая (на больших данных) | Средняя | Средняя | Ограничено |
| React Flow | Средняя | Низкая | Высокая | UI-ориентирован |
| Cytoscape.js | **Высокая** | **Высокая** | **Высокая** | Лучший выбор |

### Пример кода выбранного решения

```javascript
import cytoscape from 'cytoscape';
import dagre from 'cytoscape-dagre';

cytoscape.use(dagre);

const cy = cytoscape({
  container: document.getElementById('cy'),
  elements: [
    { data: { id: 'a' } },
    { data: { id: 'b' } },
    { data: { id: 'c' } },
    { data: { source: 'a', target: 'b' } },
    { data: { source: 'a', target: 'c' } }
  ],
  layout: {
    name: 'dagre'
  }
});
```

## 3. Алгоритм сравнения графов учебных программ

Для сопоставления учебных программ и автоматического формирования рекомендаций по их улучшению был разработан многоуровневый алгоритм сравнения графов. В основе подхода лежит анализ подтем (учебных единиц) с использованием нормализации текста, метрик строкового сходства и верификации через большую языковую модель GigaChat.

### 3.1 Нормализация и предобработка данных

Перед началом любого сравнения все текстовые данные проходят этап нормализации. Это необходимо для устранения незначительных вариаций в написании, которые не влияют на смысл, но могут помешать автоматическому сопоставлению.

Процесс нормализации включает приведение строки к нижнему регистру, замену буквы «ё» на «е», удаление всех символов, не являющихся буквами или цифрами, а также схлопывание множественных пробелов в одиночные. Такой подход позволяет сравнивать «Программирование», «ПРОГРАММИРОВАНИЕ» и «Программирование!» как идентичные сущности, что критически важно для корректного анализа учебных материалов из разных источников.

### 3.2 Нормализация структуры учебной программы

Исходные данные, получаемые из RDF-хранилища, могут иметь различные форматы представления учебной программы. В зависимости от способа загрузки и источника, структура дисциплин, тем и подтем может отличаться. Этап нормализации структуры приводит все программы к единому унифицированному виду.

В процессе нормализации извлекается название программы и список дисциплин. Каждая дисциплина приводится к стандартному формату, содержащему название дисциплины, список предшествующих дисциплин и вложенную структуру тем с подтемами. Такой подход обеспечивает единообразие входных данных для всех последующих этапов сравнения независимо от исходного формата.

### 3.3 Извлечение индексного хранилища подтем

Для эффективного поиска и сопоставления подтем строится индексное хранилище. Этот процесс обходит всю структуру тем учебной программы и для каждой дисциплины формирует множество входящих в неё подтем. В результате создаётся словарное отображение, где ключом выступает название дисциплины, а значением — множество всех подтем, встречающихся в рамках этой дисциплины.

Такая структура данных позволяет быстро проверять наличие конкретной подтемы в программе, получать перечень всех подтем для заданной дисциплины и вычислять пересечения между множествами подтем разных программ. Индексное хранилище является ключевым компонентом для последующего расчёта процентов покрытия и выявления отсутствующих элементов.

### 3.4 Многоуровневая метрика сходства подтем

Сердцем алгоритма сравнения является метрика, определяющая семантическую близость двух подтем. Вместо использования одного метода применён каскадный многоуровневый подход, где каждый следующий уровень включается только при недостаточной уверенности на предыдущем.

**Первый уровень — точное совпадение.** После нормализации строки сравниваются на полную идентичность. Если они совпадают, метрика возвращает максимальное значение 1.0, так как это наиболее надёжный случай. Этот уровень обрабатывает простейшие ситуации за доли секунды.

**Второй уровень — вхождение.** Если одна строка полностью содержится внутри другой после нормализации, метрика возвращает значение 0.9. Это покрывает случаи, когда одна подтема является уточнением другой, например «базы данных» и «реляционные базы данных».

**Третий уровень — токенный анализ.** Строки разбиваются на отдельные слова (токены), и вычисляется пересечение множеств токенов. Если доля пересечения составляет не менее 50%, возвращается значение, равное максимуму из 0.75 и полученной доли пересечения. Этот уровень эффективен для сравнения сложных составных названий, где отдельные слова могут совпадать, но порядок может различаться.

**Четвёртый уровень — строковая метрика на основе последовательного совпадения.** Используется алгоритм из библиотеки `difflib`, который вычисляет коэффициент схожести строк с учётом порядка символов. Этот метод хорош для сравнения текстов с опечатками или незначительными вариациями.

**Пятый уровень — верификация через большую языковую модель GigaChat.** Если строковое сходство находится в диапазоне от 30% до 75%, что соответствует неопределённому случаю, выполняется запрос к GigaChat. Нейросетевая модель анализирует семантику двух фраз и определяет, являются ли они разными названиями одной и той же учебной единицы. При подтверждении схожести возвращается значение 0.9. Этот уровень позволяет корректно сопоставлять синонимичные и семантически близкие понятия, которые алгоритмы строкового сравнения не способны распознать.

### 3.5 Расчёт процента покрытия подтемы

Для каждой подтемы целевой программы вычисляется, насколько широко она представлена в наборе сравниваемых программ. Этот процент является ключевой метрикой для принятия решений о рекомендациях.

Процесс вычисления начинается с того, что берётся конкретная подтема из целевой программы. Затем последовательно перебираются все программы из списка сравнения. Для каждой из них строится индексное хранилище подтем, после чего выполняется поиск семантически близкой подтемы с использованием описанной выше многоуровневой метрики. Порог схожести, при котором подтема считается соответствующей, установлен на уровне 0.75.

После проверки всех сравниваемых программ вычисляется процент: количество программ, в которых найдена соответствующая подтема, делится на общее количество сравниваемых программ и умножается на 100. Полученное значение показывает, насколько типичной или распространённой является данная подтема среди референтных программ.

### 3.6 Выявление отсутствующих подтем

Одной из ключевых задач алгоритма является обнаружение подтем, которые присутствуют в сравниваемых программах, но отсутствуют в целевой. Это позволяет выявить пробелы в учебной программе и сформировать рекомендации по их заполнению.

Процесс выявления начинается со построения индексного хранилища всех подтем целевой программы. Затем для каждой сравниваемой программы обходятся все её дисциплины и входящие в них подтемы. Для каждой такой подтемы проверяется, существует ли семантически близкая ей подтема в целевом индексе с порогом схожести не менее 0.75.

Если соответствующая подтема не найдена в целевой программе, она добавляется в счётчик с указанием дисциплины, в которой она была обнаружена. После обработки всех сравниваемых программ для каждой кандидатной подтемы вычисляется процент встречаемости — доля программ из выборки, в которых она присутствует.

Финальным этапом является фильтрация: в результат включаются только те подтемы, процент встречаемости которых достигает заданного порога (по умолчанию 70%). Такой подход гарантирует, что рекомендации будут основаны на действительно значимых и распространённых учебных единицах, а не на единичных или случайных вхождениях. Результат сортируется по убыванию процента встречаемости, чтобы наиболее важные рекомендации оказались на первом месте.

### 3.7 Формирование итогового отчёта и рекомендаций

Финальным этапом работы алгоритма является сборка детального отчёта о сравнении и генерация практических рекомендаций по улучшению учебной программы.

**Структурирование результатов.** Для каждой дисциплины целевой программы и каждой входящей в неё подтемы вычисляется процент покрытия. Эта информация сохраняется в выходной структуре, что позволяет пользователю видеть не только итоговые рекомендации, но и детальную аналитику по каждому элементу программы: какая подтема хорошо представлена в других программах, а какая — недостаточно.

**Рекомендации на удаление.** Если подтема в целевой программе имеет процент покрытия 35% или ниже, это означает, что данная учебная единица редко встречается в сравниваемых программах. Алгоритм формирует рекомендацию рассмотреть возможность удаления такой подтемы из целевой программы, так как она, вероятно, является избыточной или устаревшей.

**Рекомендации на добавление.** Для подтем, выявленных на этапе поиска отсутствующих элементов и имеющих процент встречаемости 70% и выше, формируется рекомендация добавить их в целевую программу. В рекомендации указывается название подтемы, дисциплина, к которой она относится, и процент встречаемости среди сравниваемых программ. Это даёт пользователю полную информацию о том, насколько значимым является предлагаемое дополнение.

**Обработка пограничных случаев.** Если в процессе сравнения не было выявлено ни одного расхождения, достойного рекомендации, в выходной отчёт добавляется информационное сообщение о том, что сравнение выполнено и явных расхождений не найдено. Это позволяет пользователю отличать ситуацию отсутствия проблем от технической невозможности сформировать рекомендации.

### 3.8 Обоснование выбора алгоритма

Выбор описанного многоуровневого комбинированного подхода обусловлен рядом факторов, связанных с особенностями предметной области и техническими ограничениями.

**Отказ от чистого строкового сравнения.** Исключительно строковые метрики, такие как расстояние Левенштейна или косинусная мера, не способны распознавать семантическую близость между разными по написанию понятиями. Например, «объектно-ориентированное программирование» и «ООП» с точки зрения строкового сходства будут признаны совершенно разными сущностями, хотя в образовательном контексте это одна и та же учебная единица. Кроме того, строковые методы дают ложноположительные срабатывания на технически различных, но лексически похожих терминах.

**Отказ от исключительного использования LLM.** Применение большой языковой модели для каждого сравнения привело бы к неприемлемым задержкам при анализе программ, содержащих сотни подтем. Каждый запрос к GigaChat занимает от 0.5 до 2 секунд, что в совокупности дало бы десятки минут обработки. Кроме того, такой подход повлёк бы значительные финансовые затраты, особенно при регулярном использовании в production-среде. Наконец, использование LLM для простых случаев точного совпадения или очевидного вхождения является избыточным и неоправданным.

**Обоснование комбинированного подхода.** Разработанный каскадный метод обеспечивает оптимальный баланс между точностью, производительностью и стоимостью. Ранние уровни сравнения (точное совпадение, вхождение, токенный анализ) обрабатывают более 80% всех случаев без какого-либо обращения к внешним сервисам, что гарантирует высокую скорость работы. LLM-верификация подключается только в пограничных ситуациях, когда строковые методы не могут принять уверенного решения (сходство в диапазоне 30–75%). При этом количество таких вызовов минимизировано, что сохраняет приемлемую стоимость и производительность. Пороги схожести и встречаемости настраиваются в зависимости от специфики предметной области, что делает алгоритм гибким и адаптируемым к разным типам учебных программ.

### 3.9 Вывод

В результате анализа был выбран **комбинированный многоуровневый алгоритм сравнения графов учебных программ** с использованием нормализации текста, каскадных метрик строкового сходства и LLM-верификации через GigaChat.

**Причины выбора:**
- Максимальная точность сопоставления учебных единиц за счёт комбинирования различных методов.
- Оптимальная производительность благодаря каскадной архитектуре с ранним выходом на простых случаях.
- Управляемая стоимость использования LLM за счёт выборочного обращения только в неопределённых ситуациях.
- Интерпретируемость результатов в виде процентов покрытия и конкретных рекомендаций.
- Гибкость настроек порогов для адаптации под разные предметные области.

Альтернативные подходы — исключительно строковые метрики, полная LLM-верификация или чисто статистические методы — были отклонены из-за недостаточной точности, неприемлемой производительности или высокой стоимости.
